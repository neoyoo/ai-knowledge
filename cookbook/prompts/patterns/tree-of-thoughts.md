# Tree of Thoughts (ToT)

> 将推理过程从线性链扩展为树状搜索，探索多条路径并评估回溯，解决需要探索和规划的复杂问题。

## 本质

CoT 是一条路走到黑——模型从问题出发，沿着一条推理链一直走到答案。这在大多数场景够用，但遇到真正复杂的问题时会失败：走错了方向，没有办法回头。

ToT 的思路像下棋：站在每个决策点，同时考虑多条走法，评估哪条更有希望，选最好的继续，走不通就退回来换路。具体来说，它把推理过程组织成一棵树——每个节点是一个"中间想法"（thought），从每个节点可以生成多个子节点（分支），并用评估函数给每个节点打分，再用搜索算法（BFS/DFS/Beam Search）决定如何遍历这棵树。

核心机制的三个要素：

1. **Thought 分解** — 把问题切成若干步，每步产生一个"中间想法"（可以是一个句子、一个方程、一段代码）
2. **候选生成** — 每个节点生成 k 个候选 thought（采样或逐个提议）
3. **节点评估** — LLM 自己给每个候选打分（"sure/maybe/impossible"），或给出数值分数，决定值不值得继续探索

这个框架由 Yao et al. (2023) 和 Long (2023) 几乎同时提出，两者都用树搜索增强 LLM 推理能力，主要区别在于搜索策略：Yao 用通用的 BFS/DFS/Beam Search，Long 用强化学习训练的 ToT Controller（能从数据中学习，类比 AlphaGo vs 暴力搜索）。

## 什么时候用

**需要探索多种方案的创意任务** — 写小说情节、设计产品方案、头脑风暴。问题没有唯一正确路径，不同起点会通往不同但各有价值的结果，探索比优化更重要。

**数学证明和逻辑谜题** — Game of 24（用4个数字凑出24）、数独、逻辑推演。这类问题有明确的"走得通/走不通"判断标准，每步的对错可以用规则验证，回溯有意义。

**代码生成中的多路径决策** — 设计一个复杂算法时，可以同时探索递归/迭代/动态规划三种思路，分别评估时间复杂度，选最优实现。

**规划类任务** — 旅行规划、项目计划、资源调度。需要考虑约束条件并回溯不满足约束的分支。

**共同条件** — 问题可以拆成若干步、每步有明确的"好/坏"评估标准、路径数量有限（不会组合爆炸）。

## 什么时候不用

**线性推理足够的任务** — 大多数问答、解释、翻译、摘要。用 CoT 就够，ToT 是大炮打蚊子，成本高收益低。

**无法评估中间步骤的任务** — 如果你无法判断一个中间想法"好不好"，评估函数就没意义，树搜索退化为随机探索。评估函数的质量直接决定 ToT 的效果上限。

**成本敏感场景** — ToT 的调用量是 CoT 的数倍到数十倍（每个节点都是至少一次 LLM 调用）。高并发或延迟敏感的产品不适合用在热路径上，可以考虑离线预计算或只在关键决策点启用。

**开放式生成** — 纯创意写作（不需要评估对错）、情感表达、对话交流。这类任务本来就没有"走不通"的概念，树搜索引入的框架反而会压制流动性。

## 模板

### 基础版：单 Prompt 多专家模拟

最低成本的 ToT 实现，由 Hulbert (2023) 提出——用一个 prompt 让 LLM 同时模拟多个专家的思路，评估后收敛：

```text
请想象三位不同的专家在共同回答这个问题。
每位专家先写出自己推理的第一步，然后与其他人分享。
接着所有专家进行下一步推理，依此类推。
如果任何专家在某个节点意识到自己的思路走不通，就退出这条路径。

问题：{{problem}}
```

示例 — 数学谜题：

```text
请想象三位不同的专家在共同解题。
每位专家先写出自己推理的第一步，然后与其他人分享。
接着所有专家进行下一步推理，依此类推。
如果任何专家在某个节点发现当前路径无解，就退出。

问题：用数字 2、8、4、12 各使用一次，通过加减乘除凑出 24。
```

这个变体在单次 LLM 调用里完成了"生成多路径 + 评估 + 回溯"的全流程，适合快速原型，代价是不能真正回溯（只是模拟）。

### 标准版：显式多步搜索

需要多次 LLM 调用，但能真正做到生成、评估、剪枝、回溯。以下是一个三步问题的 BFS 框架：

**Step 1 — 生成候选 thoughts（在每个节点执行）：**

```text
当前问题：{{problem}}
已有推理路径：{{current_path}}

请生成 {{k}} 个不同的下一步推理方向。每个方向用一句话描述，编号列出。
要求：方向之间要有实质差异，不是同一思路的重复表达。

格式：
1. [方向一]
2. [方向二]
...
```

**Step 2 — 评估每个候选（在同一节点执行）：**

```text
当前问题：{{problem}}
当前推理路径：{{current_path}}
候选下一步：{{candidate}}

请评估这个候选步骤对解决问题的价值：
- sure：这个方向明确能通向答案
- maybe：有希望，值得继续探索
- impossible：这个方向走不通，存在明显矛盾或死路

评估理由（一句话）：
评估结论：[sure / maybe / impossible]
```

**Step 3 — 聚合与决策（由外部逻辑或 LLM 执行）：**

保留所有 "sure" 和 "maybe" 的候选，丢弃 "impossible"。按评分排序，取 top-b 继续扩展（b 是 beam width）。

### Agent 集成版：自主树搜索

在 agent 的 system prompt 中内置 ToT 指令，让 agent 自主决策何时分支、何时回溯：

```text
你是一个问题求解 agent，使用树状搜索策略推理。

工作方式：
1. 面对复杂问题时，先生成 2-3 个不同的解题路径假设
2. 对每个假设评估可行性（可行/不确定/不可行）
3. 选择最有希望的路径继续深入
4. 如果当前路径遇到矛盾或死路，明确标注"回溯"，切换到次优路径
5. 继续推进直到找到完整解

推理格式：
<explore>
路径 A：[一句话描述]
路径 B：[一句话描述]
路径 C：[一句话描述]
</explore>

<evaluate>
路径 A：[可行/不确定/不可行] — [理由]
路径 B：[可行/不确定/不可行] — [理由]
路径 C：[可行/不确定/不可行] — [理由]
选择：路径 X，因为 [理由]
</evaluate>

<pursue>
[沿选定路径继续推理...]
</pursue>

如遇死路：
<backtrack>
路径 X 失败：[原因]
切换到：路径 Y
</backtrack>
```

## 变体

**BFS（广度优先搜索）** — 每一步同时探索所有候选，保留评分最高的 b 个，再同时扩展下一层。优点：不会陷入局部最优，能找到全局最短路径。缺点：内存和调用量随层数指数增长。适用于：问题深度有限（3-5步）、需要保证找到最优解的场景。

**DFS（深度优先搜索）** — 选一条路走到底，失败了再回溯尝试下一条。优点：内存占用低，有时能快速找到答案。缺点：容易陷入局部最优或深层死路。适用于：问题深度大但宽度小、存在明显启发式线索的场景。

**Beam Search** — BFS 的剪枝版本，每层只保留 top-b 个候选（beam width=b）。在探索宽度和计算成本之间取平衡。b=1 退化为贪心搜索（等同于 CoT），b=∞ 退化为完整 BFS。实践中 b=3-5 通常够用。

**ToT Controller（RL 驱动）** — Long (2023) 提出，用强化学习训练一个专门的控制器决定何时回溯、回溯几层。优点：能从问题数据中学习最优搜索策略，不需要手工设计搜索启发式。缺点：需要训练数据和 RL 基础设施，工程复杂度高。适合：需要在特定领域大规模部署 ToT 的场景。

**单 Prompt ToT（Hulbert 变体）** — 用"多专家讨论"的 prompt 在单次调用中模拟 ToT。成本最低，不需要外部循环逻辑，但回溯是模拟的而非真实的。适合：快速验证、成本受限、不需要严格搜索保证的场景。

## 组合与选择

**ToT vs CoT** — CoT 是单路径推理，ToT 是多路径搜索。CoT 更快更便宜，适合大多数推理任务。ToT 适合有明确"走不通"判断标准、需要探索多种可能性的复杂任务。判断标准：如果你的任务有时候 CoT 推到一半发现走错了路，就考虑 ToT。

**ToT + Self-Consistency** — Self-Consistency 在最终答案层面采样多次取多数，ToT 在推理中间层面探索多路径。两者可以叠加：先用 ToT 得到最优推理路径，再对最终步骤多次采样验证。适用于精度要求极高的场景，代价是成本再乘以采样次数。

**ToT + ReAct** — ReAct 用工具调用获取外部信息，ToT 用树搜索探索推理路径。在每个 ToT 节点上，可以触发 ReAct 循环来验证当前 thought 的可行性（如：搜索验证某个事实、执行代码检验算法正确性）。这是 agent 处理复杂研究或编程任务的强力组合。

**ToT vs Prompt Chaining** — Prompt Chaining 是线性的多步调用，每步输出作为下步输入。ToT 是树状的多分支多步调用。如果你的任务只需要线性拆解，用 Prompt Chaining 更简单；如果步骤间存在分支决策，用 ToT。

## 模型差异

| 模型 | 表现描述 | 注意事项 |
|------|---------|---------|
| Claude 4 | extended thinking 模式下内置了类似 ToT 的多路径探索能力；标准模式下用显式 ToT prompt 效果稳定，`<explore>/<evaluate>/<pursue>` 格式遵从度高 | extended thinking 已经做了部分 ToT 的工作，两者叠加可能过度冗余；先测 extended thinking 单独效果再决定是否加 ToT |
| GPT-4 / o1 / o3 | o1/o3 系列内部推理过程包含多路径探索，ToT 效果被内化；GPT-4 标准版需要显式 ToT prompt，多专家变体效果较好 | o1/o3 的内部搜索不可见也不可控，无法自定义评估函数；需要精细控制搜索策略时用 GPT-4 + 显式 ToT |
| Gemini 2 | Flash Thinking 模式有类似推理能力；标准模式下 ToT prompt 遵从度中等，复杂格式容易走形 | 建议用更简单的单 prompt 多专家变体，减少格式要求；长对话下节点状态容易混乱 |
| 开源模型（LLaMA 3、Qwen 2.5、DeepSeek） | 70B+ 参数模型能较好遵从显式 ToT 格式；小模型（<13B）评估函数质量差，"sure/maybe/impossible" 判断不可靠 | 开源模型 self-evaluation 能力弱是 ToT 的瓶颈，评估步骤要给出更多提示和示例；DeepSeek-R1 内置推理是例外 |

## 常见踩坑

**评估函数质量是成败关键** — 现象：ToT 探索了很多路径，但最终选出的路径并不比 CoT 好。原因：LLM 给中间步骤的评分不准确，"sure/maybe/impossible" 的判断含噪声，好路径被剪掉，坏路径被保留。避免方式：评估 prompt 要具体化，给出清晰的评估标准和反例；对高价值任务考虑多次采样评估再取平均；或引入外部验证工具（代码执行、规则检查）替代 LLM 评估。

**搜索空间爆炸** — 现象：分支数 k 设大了、步骤数 n 设多了，调用量变成 k^n 量级，成本失控。原因：没有合理设置搜索宽度和深度上限。避免方式：保守起点——先试 k=2, n=3，根据任务复杂度逐步调整；始终设置 beam width 上限；对"impossible"节点立即剪枝，不要等到叶节点。

**节点状态传递不完整** — 现象：模型在第 3 步忘记了第 1 步建立的约束，产生自相矛盾的路径。原因：每次调用只传入了当前节点的 thought，没有传入完整的推理路径上下文。避免方式：每次调用都把从根节点到当前节点的完整路径传入 prompt；对长路径考虑压缩摘要以节省 token。

**把 ToT 用在不需要探索的任务上** — 现象：花了 10 倍成本，结果和 CoT 差不多甚至更差。原因：任务本来就是线性的，没有真正的分支决策点，ToT 探索的"多条路径"其实是同一条路的不同表达。避免方式：在引入 ToT 前问自己："这个任务有没有可能走错路然后需要回头？"如果没有，用 CoT 就够了。

**单 prompt 多专家变体的局限** — 现象：用了多专家 prompt，但模型的三个"专家"给出几乎相同的答案，没有真正探索不同路径。原因：LLM 倾向于一致性，在单次生成中很难真正维持多个独立视角。避免方式：在 prompt 中明确要求"每个专家的方法必须与其他专家有实质差异"；或用真正的多次调用（多轮 LLM 请求）而非单 prompt 模拟。
