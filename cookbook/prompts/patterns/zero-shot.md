# Zero-shot Prompting

> 不给任何示例，直接用指令让模型完成任务。是最基础也最常用的 prompting 方式，也是所有复杂技巧的起点。

## 本质

就是直接告诉模型"做什么"，不举例子。你问，它答，没有铺垫。

这之所以可行，是因为现代大模型经过了海量数据的预训练，再经过指令微调（instruction tuning）和 RLHF 对齐，已经内化了大量任务的理解方式。"翻译这段话""给这条评论打情感标签""总结这篇文章"——这些任务模型见过太多次，不需要你再示范一遍。

Zero-shot 能行就行，不行再加 few-shot。大模型的 zero-shot 能力在持续提升，很多一两年前需要 few-shot 的任务，现在直接指令就能搞定。

## 什么时候用

**任务直白、模型理解力够** — "把这段英文翻译成中文"、"给这段代码加注释"、"用一句话总结这篇文章"。指令本身已经足够清晰，模型对任务类型熟悉，不需要示例说明期望格式。

**快速原型阶段** — 先用 zero-shot 试一下效果。如果够用，省了写示例的时间；如果不够用，输出结果也会告诉你哪里出了问题，帮你精准决定 few-shot 示例应该展示什么。

**通用能力测试与 benchmark** — 评估模型本身的能力基线时，zero-shot 才是公平的对照条件。加了示例就不是在测模型能力，而是在测模型的 in-context learning 能力。

**上下文窗口有限** — 每个 few-shot 示例都要占 token。当 prompt 空间珍贵（如塞入长文档、大段工具定义）时，zero-shot 是务实选择。

## 什么时候不用

**输出格式需要精确控制** — 如果你需要模型输出严格的 JSON 结构、特定字段命名、固定的列表格式，zero-shot 指令很难稳定保证。加 few-shot 示例直接展示期望格式更可靠，或者配合 Structured Output pattern 强制约束。

**自定义分类体系** — 标准情感分类（正/负/中）模型已经懂，但如果你的分类标签是业务特定的（如"技术问题""账单问题""投诉升级"），模型不知道各标签的边界在哪里，需要示例来校准。

**模型对任务理解偏差** — 你说"提炼核心观点"，模型理解成了逐段复述。你说"简洁"，模型给了五段话。这种偏差不是模型不够聪明，而是你的指令和模型的训练分布之间有 gap。这时候 few-shot 示例比反复修改指令更有效。

**输出需要特定风格或语气** — 语气是很难用指令精准描述的。"专业但不正式"、"简洁有力"这类描述每个模型的理解都不一样。one-shot 或 few-shot 展示一个例子，效果远好于用大段文字描述风格。

## 模板

### 基础版

直接指令，不加任何铺垫：

```text
把以下内容翻译成英文：

{{text}}
```

```text
给以下代码加上注释，解释每个函数的作用：

{{code}}
```

```text
用一句话总结以下文章的核心观点：

{{article}}
```

---

### 角色前缀版

在指令前加角色定义，帮助模型激活特定领域的知识和表达风格：

```text
你是一名资深 Python 工程师，专注于代码可读性和 Pythonic 风格。

请 review 以下代码，指出可以改进的地方：

{{code}}
```

```text
你是一名产品经理，擅长将技术需求转化为用户故事。

将以下技术说明改写为用户视角的需求描述：

{{technical_spec}}
```

角色前缀的作用不是"变成另一个实体"，而是激活训练数据中与该角色相关的知识密度和表达模式。对知识密集型任务有帮助；对简单任务加不加区别不大。

---

### 输出格式约束版

在指令中明确说明期望的输出结构，减少格式不稳定的问题：

```text
分析以下用户反馈，给出：
1. 主要问题（一句话）
2. 情感倾向（正面/负面/中性）
3. 建议的回复方向（一句话）

用户反馈：{{feedback}}
```

```text
对以下代码进行安全审查。

只报告实际存在的安全风险，格式如下：
- 风险类型：
- 影响范围：
- 修复建议：

如果没有安全风险，直接回答"未发现安全风险"。

代码：{{code}}
```

在输出格式约束里加"如果 X，则 Y"这类条件，能有效防止模型在无关情况下强行套用格式输出废话。

---

### Agent System Prompt 版

在 agent 的 system prompt 里，zero-shot 指令定义 agent 的行为规范：

```text
你是一个代码审查助手。

你的职责：
- 检查代码逻辑错误和潜在 bug
- 指出不符合最佳实践的写法
- 提出具体的改进建议

你不做的事：
- 不重写整个函数（除非用户明确要求）
- 不评论代码风格（除非影响可读性）
- 不给出主观喜好类建议

每次回复聚焦于最重要的 1-3 个问题，不列长清单。
```

用"你不做的事"来约束边界，比只写"你做的事"更有效，因为大模型倾向于扩展而非收缩。

## Zero-shot vs Few-shot 决策指南

**先试 zero-shot，不行再加示例。** 这不是懒，是效率。

| 情况 | 建议 |
|------|------|
| 常见 NLP 任务（翻译、摘要、分类） | Zero-shot 通常够用 |
| 输出格式有精确要求 | 直接上 few-shot，展示期望格式 |
| 模型输出方向对但细节不对 | 先优化指令，再考虑 few-shot |
| 模型完全误解任务 | Few-shot 示例比反复改指令更有效 |
| 自定义标签体系 / 业务特定分类 | 必须 few-shot，zero-shot 猜不准 |
| token 预算紧张 | 坚持 zero-shot，精简指令 |
| 需要特定风格或语气 | One-shot 示例比描述更直接 |

**大模型的 zero-shot 能力随时间提升明显。** 2022 年需要 few-shot 的任务，现在很多 zero-shot 就能做到。如果你的 few-shot 示例是两年前写的，值得重新测试 zero-shot 是否已经够用。

## 模型差异

| 模型 | Zero-shot 表现 | 注意事项 |
|------|--------------|---------|
| Claude 4 | 指令遵循能力强，对模糊指令的理解接近人类直觉；角色前缀效果稳定 | 对"请简洁"等模糊修饰词的理解较宽泛，建议配合长度约束（如"不超过50字"）明确化 |
| GPT-4 | 指令遵循稳定，输出格式规范；对结构化指令响应好 | 有时过度遵循格式指令导致内容变板，简单任务可以少用结构化约束 |
| Gemini 2 | 多语言 zero-shot 能力出色；对长文档的摘要和分析质量高 | 角色前缀有时被过度解读，导致回复风格过于戏剧化；业务场景建议测试效果 |
| 开源模型（LLaMA 3、Qwen 2.5） | 70B+ 模型 zero-shot 能力接近闭源；小模型（7B以下）对复杂指令理解不稳定 | 小模型建议用更简短、更直接的指令；复杂任务上 few-shot 收益明显大于闭源模型 |

## 常见踩坑

**指令模糊导致输出不可控** — 现象：每次运行输出长度、格式、侧重点都不同，无法用于需要一致性的场景。根本原因：指令留了太多解释空间。修复方式：把隐含的期望显性化。不要说"总结一下"，要说"用三句话总结，每句话对应一个核心论点"。

**过度依赖模型的默认行为** — 现象：不同版本的同一模型、或不同模型厂商，对同一 zero-shot 指令输出差异很大。原因：zero-shot 的行为由模型训练决定，不由你控制。代价：prompt 不可移植，换个模型就要重调。缓解方式：对格式敏感的场景显式约束输出结构；对风格敏感的场景加 few-shot 锚点。

**不同模型对同一指令理解力差异大** — 现象：在 Claude 4 上完美工作的 zero-shot prompt，放到 7B 开源模型上完全失效。原因：zero-shot 能力本质上依赖预训练和对齐质量，不同模型差距显著。工程应对：在多目标模型上都要测试；如果要跨模型兼容，用 few-shot 而非依赖 zero-shot 理解力。

**角色前缀滥用** — 现象：给每个任务都加"你是XX专家"，以为能提升质量。实际效果：对简单任务没有帮助，有时反而让模型过度迎合角色定义而忽略实际指令。原则：角色前缀在知识密集型任务（医学分析、法律解读、代码审查）上有价值；对格式转换、翻译等通用任务意义不大。

**把 zero-shot 当万能方案** — 现象：任务失败时反复修改指令措辞，陷入指令调试的无限循环。正确姿势：如果优化了 2-3 次指令效果还是不好，停下来想想这个任务是不是需要 few-shot 示例，或者是否属于 zero-shot 本就不适用的场景（见"什么时候不用"）。
