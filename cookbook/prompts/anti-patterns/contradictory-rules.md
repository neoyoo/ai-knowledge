# Contradictory Rules

> 同一个 prompt 里的规则互相打架，模型陷入无法同时满足的困境，只能随机选边站。

## 症状

- 模型输出在不同轮次里"执行"不同的规则，前后不一致
- 你加了规则 A 是因为某个场景，加了规则 B 是因为另一个场景，从没想过它们会冲突
- system prompt 经过多人或多次迭代叠加，没人记得每条规则的来历
- 你发现模型有时符合预期，有时完全相反，却找不到原因

## 错误示例

```text
[System Prompt]

你是一个技术支持助手。

规则：
1. 回答要简洁，不超过 3 句话
2. 对每个问题都要详细解释原因和背景，确保用户完全理解
3. 始终使用正式的商务用语
4. 要像朋友一样亲切自然地交流
5. 不要主动推荐任何产品
6. 如果用户的问题可以通过升级套餐解决，要告知用户
```

规则 1 vs 规则 2：不超过 3 句话 vs 详细解释原因和背景——这两条本质上不可兼得。
规则 3 vs 规则 4：正式商务用语 vs 像朋友一样——语气风格直接冲突。
规则 5 vs 规则 6：不主动推荐产品 vs 告知可以升级套餐——在某些情况下完全矛盾。

模型面对冲突时的实际行为：随机加权，或偏向 prompt 中后出现的规则，或在不同 session 里表现出随机差异。

另一个更隐蔽的变体（跨层矛盾）：

```text
[System Prompt]
回答时始终保持中立，不表达个人观点。

[User Message]
你觉得这个方案哪个更好？请给出你的建议和理由。
```

system prompt 要求中立，user message 要求表达观点——模型输出会变成"两边都说一点"的无效回答，既没有真正的观点，也没有真正的中立分析。

## 为什么有害

LLM 没有"规则优先级"的内置机制。当两条规则冲突时，模型不会报错，也不会告诉你。它会选择一个路径继续生成，选择逻辑是不透明的，受 token 位置、训练分布、temperature 等因素影响。

结果是：你以为规则生效了，实际上执行的是哪条规则取决于运气。在生产环境里，这种不可预测性会表现为用户投诉"这个助手有时候这样有时候那样"，而你完全复现不了问题。

更危险的情况：矛盾规则会导致模型输出一种"折中语气"——既不够简洁也不够详细，既不够正式也不够亲切。所有规则都只被部分执行，没有一条被真正遵守。

## 正确做法

**第一步：审计你的规则，显式标注优先级**

```text
[System Prompt]

你是一个技术支持助手。

核心原则（不可违反）：
- 准确性优先：宁可说"我不确定"也不要给出错误信息

输出风格（优先级从高到低）：
1. 简洁：默认回答控制在 2-3 句话
2. 完整：如果用户明确说"详细解释"，则展开说明；否则给出简短回答并提示"需要详细说明请告诉我"
3. 语气：专业但不生硬，避免过于正式的书面用语

产品推荐原则：
- 不主动推荐付费升级
- 如果用户主动询问解决方案且升级是唯一有效途径，可以如实告知，但不要施压
```

**第二步：用场景分支替代冲突规则**

当两条规则在不同场景下都有必要时，用条件分支代替并列规则：

```text
回答长度规则：
- 技术故障排查类问题：步骤化，详细，不限长度
- 简单功能咨询：2 句话以内
- 账号/权限问题：给出直接操作步骤，无需解释原理
```

**第三步：对抗性自测**

写完规则后，对每对规则问自己：**"有没有一种用户输入，会让这两条规则指向完全相反的行为？"** 如果有，必须显式决定在这个场景里哪条优先，或合并成一条带条件的规则。

## 修复检查清单

- [ ] 列出 system prompt 里的所有规则（提取出来，逐条对比）
- [ ] 对每对规则做冲突测试：找一个可能同时触发两条规则的 user input，看它们是否冲突
- [ ] 长度/详细度相关的规则是否只有一条或有明确的条件分支？
- [ ] 语气/风格相关的规则是否统一或有场景区分？
- [ ] 推荐/不推荐相关的规则是否有清晰的触发条件？
- [ ] 规则之间是否有显式的优先级声明？
- [ ] 在加新规则之前，是否检查过它和现有规则的兼容性？
