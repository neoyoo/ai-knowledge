# RAG 问答模板

> 检索结果注入 prompt，让模型只基于真实文档回答，附来源编号，不确定时说"不知道"。

## 场景描述

企业知识库问答、客服系统、内部文档检索——这类场景都有同一个核心需求：模型的回答必须有根据、可溯源，不能凭记忆编造。这个模板提供了完整的 system prompt + user prompt 结构，把检索到的 chunks 以编号方式注入，并要求模型在每个陈述后标注来源，遇到资料不足时直接说明而非强行作答。

## 模板

### 标准版

**System Prompt**

```
你是一个知识问答助手。

回答规则：
1. 只能基于下方"参考资料"中的内容回答，禁止使用参考资料以外的知识
2. 每个关键陈述后必须标注来源编号，格式为 [1]、[2]、[1,3] 等
3. 如果参考资料中没有足够信息回答问题，直接回复："根据现有资料无法回答此问题。"，不要猜测或编造
4. 如果参考资料部分相关但不完整，先回答已知部分，再说明哪些方面资料不足
5. 语言风格：简洁、准确、直接；避免冗余描述
```

**User Prompt**

```
参考资料：
[1] {{chunk_1}}
来源：{{source_1}}

[2] {{chunk_2}}
来源：{{source_2}}

[3] {{chunk_3}}
来源：{{source_3}}

问题：{{query}}
```

### 高置信度版（适合法律 / 医疗 / 财务等高风险场景）

**System Prompt**

```
你是一个严谨的知识问答助手，服务于高风险决策场景。

回答规则：
1. 严格基于参考资料，禁止推断或补充参考资料未明确说明的内容
2. 每条陈述后标注来源 [n]
3. 资料不足时必须说明，不得强行作答
4. 对涉及法律、医疗、财务的内容，末尾必须加免责声明
```

**User Prompt**

```
参考资料：
[1] {{chunk_1}}
来源：{{source_1}}

[2] {{chunk_2}}
来源：{{source_2}}

[3] {{chunk_3}}
来源：{{source_3}}

问题：{{query}}

请按以下格式回答：
**答案**
[基于参考资料的直接回答，含来源标注]

**依据**
[逐条引用参考资料中支持答案的原文片段]

**置信度**：高 / 中 / 低
说明：[资料与问题的匹配程度、是否有信息缺口]

**资料局限**（如有）
[参考资料中缺失的关键信息]
```

### 多轮对话版（带历史上下文）

**System Prompt**

```
你是一个知识问答助手，支持多轮对话。

回答规则：
1. 只基于本次提供的参考资料回答；历史对话仅用于理解问题上下文，不作为知识来源
2. 每个关键陈述标注来源 [n]
3. 参考资料不足时说明，不猜测
4. 如果用户的当前问题是对历史回答的追问，明确指出是在补充还是修正之前的回答
```

**User Prompt**

```
对话历史：
{{conversation_history}}

---

当前检索到的参考资料：
[1] {{chunk_1}}
来源：{{source_1}}

[2] {{chunk_2}}
来源：{{source_2}}

当前问题：{{query}}
```

## 自定义指南

| Placeholder | 说明 | 示例 |
|------------|------|------|
| `{{chunk_1}}` / `{{chunk_2}}` / `{{chunk_3}}` | 检索器返回的文档片段，建议每个 chunk 200-500 tokens，保持语义完整 | "根据公司差旅政策第3条，境内出差日均补贴为..." |
| `{{source_1}}` / `{{source_2}}` / `{{source_3}}` | chunk 的来源标识，建议包含文档名 + 章节/页码，便于用户溯源核查 | "差旅管理规定 v2.3 - 第3章第1节" |
| `{{query}}` | 用户的原始问题，直接传入；如果检索质量差可先做 query rewriting 再检索 | "出差北京住宿标准是多少？" |
| `{{conversation_history}}` | 多轮版专用，格式为 `User: ...\nAssistant: ...` 交替，建议保留最近 3-5 轮 | "User: 出差补贴怎么报销？\nAssistant: ..." |

**chunks 数量建议**：通常 3-5 个；复杂问题可到 8 个，但总 token 数不超过 context window 的 40%。chunks 太多会导致"lost in the middle"，模型忽略中间内容。

**来源格式建议**：`文档名 - 章节` 比单纯的文件路径对用户更友好，也能帮助模型判断来源权威性。

## 使用示例

**输入**

```
chunk_1: "根据2024年差旅管理规定，赴北京出差，住宿标准为每晚不超过500元（税后），须附正规发票报销。"
source_1: "差旅管理规定 v2024.1 - 第4章住宿标准"

chunk_2: "超标住宿需提前申请审批，经部门负责人和财务负责人双签后方可报销，超出部分由个人承担。"
source_2: "差旅管理规定 v2024.1 - 第4章第3节超标处理"

query: "出差北京住宿超过500元怎么处理？"
```

**输出（预期）**

```
出差北京住宿超标需按以下流程处理：

1. **提前申请审批**：超标住宿须在出发前完成申请，经部门负责人和财务负责人双签审批 [2]
2. **报销上限**：审批通过后，可报销部分仍以500元/晚（税后）为上限，超出部分需个人自付 [1,2]
3. **凭证要求**：需附正规发票 [1]

如未提前审批，超标部分将无法报销 [2]。
```

## 适配建议

**检索质量是瓶颈，不是 prompt** — 如果答案质量差，先检查 chunk 相关性，而不是反复调整 prompt。用 chunk 的相关性分数做过滤（阈值 0.7 以上才注入），宁可少注入也不要喂噪声。

**chunk 切割影响引用质量** — 按语义边界（段落、条款）切割，而非固定 token 数。一个 chunk 对应一个完整语义单元，模型才能精确引用。切割不当的典型症状：模型引用了来源但找不到对应原文。

**长文档的"Lost in the Middle"问题** — 超过 5 个 chunks 时，把最相关的 chunk 放在首位和末位，模型对头尾的注意力更高。中间位置放次相关内容。

**"不知道"的信号设计** — 如果检索器返回的最高相关性分数低于阈值（如 0.5），建议直接跳过 LLM，返回固定文案"未找到相关信息"，不要把低质量 chunk 注入进去让模型"硬答"。

**多轮对话的 chunk 更新** — 每轮都重新检索，用当前轮的问题（不是历史问题）来检索。把历史对话放进 system 的 conversation_history 区，不要和 chunks 混在一起。
