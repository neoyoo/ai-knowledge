# Classification Template

> 把文本输入映射到预定义类别，从简单的单标签分类到带置信度的多标签路由，覆盖 agent 中最常见的意图识别和内容分发场景。

## 场景描述

分类是 agent 系统中最基础的路由机制。用户输入进来，第一步通常就是"这个请求属于哪类"——然后才能决定调哪个工具、走哪条流程、给哪个下游 agent。

分类 prompt 设计的核心张力：**类别定义的精确度 vs 模型的泛化能力**。

- 类别太宽泛 → 模型不知道边界在哪，边界案例会随机归类
- 类别太细 → 模型需要区分相似类别，容易混淆，且 prompt 越来越长
- 没有示例 → 模型按自己的理解分，和你的业务定义可能不一致
- 示例太多 → context 消耗大，维护成本高

实践中最有效的策略是：**从 zero-shot 开始，在边界案例上加 few-shot**。不要一上来就用 5-shot，先看哪些类别容易混淆，然后针对性地给那几个类别加示例。

## 模板

### 1. Zero-shot 单标签分类

适用于：类别定义清晰、与通用语言理解高度对齐的任务

```text
将以下文本归类到下列类别之一。

类别：
{{#each categories}}
- {{name}}：{{description}}
{{/each}}

规则：
- 只输出类别名称，不要解释
- 如果不属于任何类别，输出 "其他"

文本：{{input}}

类别：
```

实际使用时展开为：

```text
将以下文本归类到下列类别之一。

类别：
- 账单问题：关于付款、发票、退款、订阅费用的问题
- 技术故障：产品功能不工作、报错、性能问题
- 使用咨询：如何使用某功能、操作流程、最佳实践
- 账户管理：注册、登录、密码、权限、账户信息修改

规则：
- 只输出类别名称，不要解释
- 如果不属于任何类别，输出 "其他"

文本：{{input}}

类别：
```

### 2. Few-shot 分类（针对性示例）

适用于：类别定义与通用理解有偏差、或边界案例容易混淆的任务

```text
将文本归类到以下类别：{{categories_list}}

示例：

{{#each examples}}
文本：{{this.text}}
类别：{{this.label}}

{{/each}}
文本：{{input}}
类别：
```

实际使用时，示例要有针对性——覆盖容易误判的边界：

```text
将文本归类到以下类别：正面、负面、中性

示例：

文本：快递比预期慢了两天，但包装很完整。
类别：中性

文本：产品还不错，就是说明书全是英文。
类别：中性

文本：收到货发现是翻新机，完全不能接受。
类别：负面

文本：快速发货，比描述的更好！
类别：正面

文本：{{input}}
类别：
```

注意：示例集中覆盖了"正负面混合"的中性案例（最常误判的边界），而不是每个类别均等给 1-2 个。

### 3. 多标签分类（一个输入对应多个标签）

适用于：内容标签、文章分类、需求分析（一个需求可能涉及多个模块）

```text
为以下文本打标签。从候选标签中选择所有适用的标签，可以选多个，也可以一个都不选。

候选标签：{{tags_list}}

规则：
- 以 JSON 数组格式输出，如 ["标签A", "标签B"]
- 只输出数组，不要解释
- 如果没有适用标签，输出空数组 []
- 置信度低于 70% 的标签不要加

文本：{{input}}

标签：
```

### 4. 意图路由分类（agent 分发场景）

适用于：multi-agent 系统中将用户输入路由到不同处理流程

```text
你是一个请求路由器。分析用户输入，判断应该由哪个处理流程接管。

可用流程：
{{#each routes}}
- {{name}}：{{trigger_condition}}
{{/each}}

路由规则：
- 输出 JSON，格式：{"route": "流程名称", "confidence": 0-100, "reason": "一句话说明"}
- confidence < 60 时，route 填 "human_handoff"（转人工）
- 如果输入包含多个意图，选择优先级最高的一个

用户输入：{{user_input}}

路由结果：
```

实际使用时展开为：

```text
你是一个请求路由器。分析用户输入，判断应该由哪个处理流程接管。

可用流程：
- billing_agent：涉及费用、发票、退款、账单查询
- tech_support_agent：产品功能异常、报错、性能问题
- sales_agent：询价、购买意向、套餐对比
- faq_agent：通用问答、使用说明、政策查询

路由规则：
- 输出 JSON，格式：{"route": "流程名称", "confidence": 0-100, "reason": "一句话说明"}
- confidence < 60 时，route 填 "human_handoff"（转人工）
- 如果输入包含多个意图，选择优先级最高的一个

用户输入：{{user_input}}

路由结果：
```

### 5. 带置信度输出（含不确定性量化）

适用于：需要兜底策略的生产系统，或置信度低时触发人工审核

```text
对以下文本进行分类，并给出置信度评估。

类别：{{categories_list}}

输出 JSON，格式：
{
  "label": "类别名称",
  "confidence": 0-100,
  "reasoning": "简短说明分类依据",
  "alternative": "次优类别（如有）"
}

置信度标准：
- 90+：非常确定，文本明确符合该类别
- 70-89：基本确定，有少量模糊之处
- 50-69：不太确定，可能属于多个类别
- < 50：高度不确定，建议人工审核

文本：{{input}}

分类结果：
```

## 自定义指南

**`{{categories_list}}`** — 类别列表。最佳实践：每个类别附上 1-2 句描述（而不只是名称），尤其是类别名称存在歧义时。描述要说明"什么情况属于这类"，而不是字典定义。

**`{{tags_list}}`** — 多标签场景的候选标签集。如果标签超过 20 个，考虑分层：先粗分类，再在匹配类别下细分标签，减少单次 prompt 的类别数量。

**`{{examples}}`** — 示例的选择原则：不要每类均等给示例，而是重点覆盖**容易混淆的边界对**。如果"正面"和"中性"最容易混淆，就多给这两类的对比示例。

**`{{routes}}`** — 意图路由场景中，流程名称要能让模型直觉理解（billing_agent 比 process_type_2 好得多）。trigger_condition 要写成可判断的条件句，不要写模糊的功能描述。

**置信度阈值** — 根据业务容错性设置：客服路由建议 70 分以上才自动处理，60 分以下转人工；内容标签场景容忍度更高，50 分以上可以接受。不要把阈值设太高（> 85），会导致大量转人工。

**"其他"类别** — 几乎所有分类系统都需要一个兜底类别。显式告诉模型"如果不属于任何类别，输出 X"，比让模型强行归类到最接近的类别更可靠。

## 使用示例

**场景：agent 意图路由**

```text
你是一个请求路由器。分析用户输入，判断应该由哪个处理流程接管。

可用流程：
- code_agent：写代码、调试、代码审查、技术实现问题
- search_agent：需要查找最新信息、事实核查、外部数据获取
- analysis_agent：数据分析、图表生成、统计计算
- general_chat：闲聊、概念解释、不需要工具的通用问答

路由规则：
- 输出 JSON，格式：{"route": "流程名称", "confidence": 0-100, "reason": "一句话说明"}
- confidence < 60 时，route 填 "human_handoff"
- 如果输入包含多个意图，选择优先级最高的一个

用户输入：帮我查一下今天 BTC 价格，然后画个过去一周的走势图

路由结果：
{"route": "search_agent", "confidence": 75, "reason": "需要实时数据获取，画图是后续步骤，先路由到 search_agent 获取数据"}
```

**场景：多标签内容分类**

```text
为以下文本打标签。从候选标签中选择所有适用的标签，可以选多个，也可以一个都不选。

候选标签：Python, JavaScript, 性能优化, 架构设计, 入门教程, 最佳实践, 安全, 测试

规则：
- 以 JSON 数组格式输出
- 置信度低于 70% 的标签不要加

文本：如何用 asyncio 避免 Python 中常见的并发陷阱，并通过单元测试验证并发行为

标签：
["Python", "性能优化", "最佳实践", "测试"]
```

**场景：带置信度的客诉分级**

```text
对以下文本进行分类，并给出置信度评估。

类别：严重客诉（涉及法律、大额损失、媒体曝光风险）、普通投诉（产品问题、服务不满）、咨询建议（改进建议、功能请求）、中性反馈（使用体验描述）

输出 JSON，格式：
{"label": "类别名称", "confidence": 0-100, "reasoning": "简短说明", "alternative": "次优类别（如有）"}

文本：你们的产品让我损失了三万块，我已经联系了消费者协会，准备投诉你们

分类结果：
{"label": "严重客诉", "confidence": 95, "reasoning": "明确提及经济损失金额和第三方机构投诉意向，符合严重客诉标准", "alternative": null}
```

## 适配建议

**在 agent tool 中使用** — 把分类 prompt 封装成工具调用，让主 agent 在需要路由时调用。工具返回值用带置信度的 JSON（模板 5），主 agent 根据置信度决定是否继续或转人工。

**类别数量超过 10 个** — 拆成两级分类。第一级粗分（3-5 个大类），第二级细分（每个大类下 3-5 个子类）。这样每次 prompt 的类别数量可控，且模型在每个层级的注意力更集中。

**需要解释分类依据** — 用模板 5 的 `reasoning` 字段，或在 prompt 末尾加：`先用一句话解释你的判断依据，然后再输出类别。` 但注意：加解释会显著增加 latency，在高吞吐场景要权衡。

**高频低延迟场景（如实时路由）** — 用 zero-shot + 简短类别描述（模板 1），去掉 reasoning，只输出类别名。避免 few-shot 增加 prompt token 数量。必要时考虑用小模型（如 Haiku/GPT-4o-mini）专门做路由，降低成本和延迟。

**类别边界随业务演变** — 分类 prompt 是强耦合业务逻辑的地方，随着业务变化类别定义也会变。建议把类别列表和描述外置到配置文件，而不是硬编码在 prompt 字符串里，方便迭代和 A/B 测试。

**验证分类质量** — 在生产前，用一批标注好的测试样本跑一遍，重点关注：混淆矩阵中哪些类别互相混淆最严重。对混淆严重的类别对，针对性地加 few-shot 示例。不要靠感觉判断质量。
